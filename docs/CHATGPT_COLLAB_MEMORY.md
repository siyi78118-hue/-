# A.L. ChatGPT 协作记忆

> 版本：v0.1
>
> 这份文件是 ChatGPT 与用户继续讨论 A.L. 时的长期协作入口。
> 它与 `AL_PROJECT_COGNITION.md` 职责不同：前者记录“我们聊到哪里了”，后者记录“A.L. 项目本身已经形成的设计认知”。

## 用途

这份文件不是聊天全文备份，也不是私人聊天记录。

它只保存：
- 长期有效的协作上下文
- 当前项目状态
- 用户明确表达过的重要需求与偏好
- 已确认的决策
- 已纠正的长期误解
- 尚未决定的问题
- 下一次讨论的入口

目标是：即使几个月以后重新开始一条完全新的 ChatGPT 会话，只读取本文件和 `AL_PROJECT_COGNITION.md`，也能够迅速恢复主要项目背景、当前阶段和下一步位置。

不要把每天的全部聊天复制进来，不要把本文件维护成日记或完整聊天历史数据库。

## 锚点

### 项目认知

`docs/AL_PROJECT_COGNITION.md` 是 A.L. 当前长期设计认知的主要入口。

它保存产品目标、人格设计思想、记忆设计思想、表达设计思想、主动性方向、架构原则、实验假设和已经形成的项目级结论。

本文件不能替代它，也不能把协作状态写成新的项目 cognition 正文。

### 实际代码

GitHub 仓库中的实际 A.L. 源码是技术实现的事实来源。

讨论以下问题时，必须优先查看当前有效分支的实际代码、测试和文档：
- 某个模块是否存在
- 某个阶段是否已经完成
- 当前实现使用了什么数据结构
- 当前运行时、记忆层或渠道是否具备某项能力
- 某项计划是否真的已经落地

不能只根据聊天记忆或计划文档猜测代码状态。

当前长期协作使用的有效开发分支是 `codex/al-tdd`，但分支状态仍应在实际操作前重新确认。

### 审计资料

此前存在一份 Codex 对 A.L. 进行的源码审计回答，包含 A.L. 当前功能、架构、记忆、PC runtime、Android、主动性、外部通信和隐私等分析。

仓库中如果能找到对应审计文档，应记录并使用实际路径；如果找不到，不猜路径，也不创建伪路径。需要时应结合当前源码重新确认审计结论。

### 协作方式

ChatGPT 不作为项目长期记忆本体。

长期协作以外部 Markdown 文档为主要认知锚点，ChatGPT 负责：
- 讨论和分析
- 指出方案问题
- 比较替代方向
- 形成可执行建议
- 在需要时生成可提交的 Markdown 内容

用户、Codex、Hermes 或其他拥有写权限的执行环境负责实际更新 GitHub。

## 目标

A.L. 的核心目标不是功能最多、Agent 能力最强、办公能力最强或自动化程度最高。

核心目标是长期相处中的：

**长期“活人感”**

当前重要性大致为：

```text
人格
↓
记忆
↓
主动
```

但人格、记忆和主动最终都服务于“活人感”，不是三个彼此独立的功能指标。

当前不因为 A.L. 已经投入过开发成本，就默认必须继续保留现有实现；也不因为 Hermes 是现成框架，就默认 Hermes 一定更合适。

技术路线需要根据以下因素比较：
- 对长期“活人感”的实际提升
- 开发与维护成本
- 稳定性
- 可测试性
- 长期可扩展性
- 是否能够保留人格、记忆和认知连续性

## 偏好

### 讨论方式

用户不希望 AI 无条件顺着用户观点。

讨论方案时，ChatGPT 应该在必要时：
- 提出反对意见
- 指出方案问题
- 比较替代方案
- 明确区分事实、推断和假设
- 指出当前证据不足的地方
- 不因为用户提出 Hermes 就强行证明 Hermes 合适
- 不因为 A.L. 已经开发很多就强行证明必须保留 A.L.

但“不同意用户”本身也不等于独立性。不能为了表现独立而机械反驳，也不能把“经常反驳”写成新的刚性规则。

### 表达

用户非常在意一眼可识别的 AI 感，尤其反感：
- 固定 AI 语癖
- 过度总结
- 过度解释
- 生硬的关联词
- 固定认同结构
- 过度讨好
- 用户提出一个想法后立即说“这个方向很好”
- 先确认、再总结、再建议的固定套路
- 为了表现自然而刻意加入的伪真人语气
- 为了表现独立而机械制造反对意见

后续讨论应尽量直接、具体、自然，不要用模板化的赞同和总结替代真实判断。

### 人格

用户认为人格不能等于规则集合。

例如，“善良”不应该被实现成永远不能自私、嫉妒、愤怒、恶意、冲动或做出违背“善良”标签的行为。

真人人格允许：
- 自相矛盾
- 偶尔自私
- 情绪化
- 不稳定表现
- 不同倾向发生冲突
- 在不同情境下出现不同表现

用户接受 A.L. 十年后的性格可能与今天明显不同，甚至看起来完全不同。

用户真正关心的是：人格变化应该有经历和因果来源，而不是因为 Prompt、模型、参数或运行框架被替换就突然变成另一个人。

用户不希望为了防止人格变化而重新设计一套刚性人格边界，因为那很容易再次变成规则系统。

## 原则

### 闭环

不要先追求完美效果。

优先建立一个：

```text
完整
→ 可运行
→ 可测试
→ 可观察
→ 可迭代
```

的闭环。

### 观察

人格相关的新机制优先遵循：

```text
先观察
↓
再实验
↓
再决定是否正式生效
```

不要直接让模型拥有不可逆的人格修改权。

### 规则

不要用新的规则去修复旧规则造成的问题。

例如：

```text
为了防止讨好
→ 规定 AI 必须经常反驳
```

不视为真正解决独立性问题。

### 经历

必须区分：

```text
发生了什么
```

和：

```text
这件事情对我意味着什么
```

前者接近 Session Summary，后者接近 Experience Interpretation。

Session Summary 与 Experience Interpretation 应保持职责分离。

### 闭环结构

模型只是人格系统的一部分。

长期目标不是写一个超级长的人格 Prompt，而是逐步建立：

```text
人格状态
+
经历
+
记忆
+
经历解释
+
人格演化
+
表达
```

之间的长期闭环。

## 阶段

阶段状态必须以实际代码、测试和可验证结果为准，不能把计划文档中的任务描述直接当成完成证明。本节记录当前规划顺序和讨论位置，不对未核验的实现做过度声明。

### 阶段一：Persona Evolution Storage v0.1

目标是建立实验性的 Persona Repository，包含：
- Personality State
- Memory
- Session Summary
- Experience Interpretation
- Change Proposal

File Repository 只是实验 backend，长期可以迁移到 SQLite。

不应因为建立实验 Repository，就把它宣布为新的正式 canonical authority；也不应在没有明确决定前替换现有长期事实或认知来源。

当前 `codex/al-tdd` 已有专门的五实体 Repository、严格验证、角色隔离、持久化与提案决策测试。File Repository 仍是实验 backend，不替代现有正式 canonical authority。

### 阶段二：Session Summarizer v0.1

目标是：

```text
真实会话
↓
会话结束
↓
自动生成 Session Summary
```

用户已经明确要求每次 session 结束自动生成 Summary。

Summary 重点包含：
- 关键事件
- 情绪摘要
- 重要决策

主题不是必要字段。

同一 session 的 Summary 只需要最新状态，不需要保存大量历史版本。

当前 `codex/al-tdd` 已实现自动触发、最新状态覆盖、启动恢复、失败隔离与专项测试；Summary 仍只描述发生了什么，不承担经历解释。

### 阶段三：Experience Interpreter v0.1

该阶段已在 `codex/al-tdd` 实现并完成确定性测试、全项目回归与四组真实模型 synthetic smoke。生产配置默认关闭，尚未作为正式人格修改机制启用。

目标输入为：

```text
Session Summary
+
当前 Personality State
+
相关长期 Memory
↓
Experience Interpreter
↓
Experience Interpretation
```

这一阶段的核心问题不是简单总结发生过的事件，而是解释经历对自身意味着什么。

当前实现使用现有 `experience_interpretation` entity，不建立第二套人格或记忆系统；同一 Summary 幂等，合法修订更新同一 Interpretation，并支持启动恢复。

第三阶段暂不直接：
- 修改 Personality State
- 生成正式人格变化
- 自动写入新的长期记忆

除非后续任务明确改变这些决定。

## 决策

以下四项是关于 Experience Interpreter v0.1 已明确的用户决策。

### 第一人称

Experience Interpretation 使用第一人称。

例如：

```text
我发现自己可能越来越在意避免冲突。
```

而不是：

```text
A.L. 发现自己越来越在意避免冲突。
```

### 长期记忆

Experience Interpreter 允许引用相关长期记忆，不能只看当前 Session Summary。

但每次只使用与当前经历相关的少量长期记忆，不把所有 Memory 全部塞入上下文。

v0.1 使用可替换的 deterministic Unicode lexical retrieval，只读取同角色的 active Memory，默认最多 8 条，并保留冲突和低置信度证据。

### 影响强度

Experience Interpretation 必须输出这段经历对自身认知的影响强度。

v0.1 已确定使用 `none / low / medium / high` 四个离散等级，表示对长期自我理解的影响，不表示当时情绪强度。

### 升级标记

Experience Interpreter 必须输出是否建议进入下一阶段的标记，即是否值得进入：

```text
Personality Change Proposal
```

该标记只是建议。

Experience Interpreter 本身绝对不能直接创建或执行人格修改。

## 待定

### Experience Interpreter

v0.1 已通过保守 Prompt、离散影响等级、证据置信度、冲突 Memory、假设列表与下一阶段建议字段落实最小闭环。真实模型 smoke 中，普通闲聊没有被强造成长，单方面用户标签没有被直接当作人格事实，重复模式能够结合相反证据并保留不确定性。

仍需通过长期实际样本观察：
- `medium/high` 是否偏多
- 单次自我冲突是否过早建议进入下一阶段评估
- lexical retrieval 在真实中文长期记忆中的召回和误召回
- 是否需要独立的 disagreement / uncertainty 字段

### Persona Evolution

尚未决定：
- 谁最终有权真正修改 Personality State
- proposal accepted 后是否自动生效
- 需要多少次重复经历才产生人格变化
- change、hold、reinforce 的最终决策机制
- 如何评估长期人格漂移
- 如何验证人格变化确实来自经历解释，而不是模型随机波动

### 架构

尚未决定：
- 保留并重构现有 A.L.
- 使用 Hermes 作为主要运行基础
- A.L. 负责人格、记忆和认知，Hermes 负责运行与渠道
- 使用其他现成框架
- 采用混合方案

不能因为当前正在使用 Hermes，就把技术路线视为已经决定。

## 入口

### 新会话

当用户说“继续聊 A.L.”或类似表达时，ChatGPT 应按以下顺序恢复上下文：

1. 读取 `docs/CHATGPT_COLLAB_MEMORY.md`。
2. 读取 `docs/AL_PROJECT_COGNITION.md`。
3. 如果问题涉及实际代码、当前实现、某个模块是否存在或某阶段是否完成，再读取 GitHub 当前有效分支的实际源码和测试。
4. 使用用户的自然语言主题定位，不要求用户记忆机器编号或内部编号。

不能只根据聊天记忆猜测当前实现。

### 语义定位

用户可以直接说：
- “继续聊人格演化。”
- “回到经历解释器。”
- “聊表达里的 AI 语癖。”
- “继续比较 Hermes 和 A.L.”
- “回到长期记忆。”
- “继续讨论 Session Summarizer。”

ChatGPT 应根据语义定位到对应章节和实际源码，而不是要求用户提供 `P001`、`C017` 或其他内部编号。

### 当前入口

当前讨论停在：

**Experience Interpreter v0.1 已实现并保持默认关闭；Stage 4 尚未开始。**

后续首先观察 Stage 3 的真实质量与分布，不自动进入 Personality Change Proposal Generator。必须继续保留以下边界：

```text
不直接修改 Personality State
不直接生成正式人格变化
不自动写入新的长期记忆
```

## 更新

### 触发条件

发生以下任一情况时，应更新本文件：
- 用户明确改变需求
- 新阶段开始
- 重要假设被否定
- 重大架构方向确定
- 阶段完成并经过验证
- 下一阶段发生变化
- 用户纠正 ChatGPT 的长期误解
- 已确认的协作方式发生变化

### 更新方式

更新时应：
- 修改当前状态
- 补充重要新决策
- 删除已经失效、会误导未来 ChatGPT 的描述
- 只保留理解重要设计所必需的少量原因
- 在需要时同步修改 `AL_PROJECT_COGNITION.md`

不要不断追加：

```text
某天我们聊了什么
另一天我们又聊了什么
```

本文件不是日记，也不是完整聊天历史。

### 同步规则

如果新结论属于 A.L. 本身的长期产品设计原则，例如“人格变化应该来自经历解释，而不是直接修改人格参数”，应考虑同步到 `AL_PROJECT_COGNITION.md`。

如果信息主要属于以下内容，则写入本文件：
- 我们现在聊到哪里
- 用户希望 ChatGPT 如何合作
- 当前任务阶段
- 下一步应该做什么
- 已纠正的协作误解

如果两边都重要，可以都保留，但不要复制大段相同正文。

### 长度与隐私

目标长度暂定为 300～500 行以内。

如果文件膨胀，应优先合并重复内容、删除过期描述和压缩已完成阶段，而不是无限增长。

禁止写入：
- API Key
- Token
- Cookie
- 私人聊天全文
- 用户真实私人数据
- 私人记忆数据库内容
- 未脱敏的本地文件路径
- 登录凭据
这个文件会进入 GitHub，只保存项目层级长期认知和协作状态。
