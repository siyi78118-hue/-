# 一键清空全部自动任务设计

## 背景

同一设备在关闭主动消息和云闹钟后，仍会从网页本地状态、Service Worker 镜像和 Android 原生执行队列恢复旧任务，并重新向 Cloudflare Worker 补排。生产排查中，同一设备和角色在云端重新累积了 131 个朋友圈任务、1 个主动私聊任务和 86 个到期桶，证明单独删除云端 KV 只能暂时消除症状。

本功能提供一个面向用户的紧急清理入口，一次停止任务生成、清除各层残留并删除该设备的云端自动任务，同时保留设备推送绑定和用户内容。

## 目标

- 在诊断页面提供“紧急清空全部自动任务”按钮。
- 清除主动私聊和主动朋友圈任务在网页、Service Worker、Android 原生队列和 Cloudflare 中的残留。
- 清理后不再补排、不再执行迟到推送，也不再继续产生自动任务错误。
- 保留角色、聊天、朋友圈正文、记忆库、API Key、模型配置、设备 ID、FCM Token 和推送订阅。
- 用户以后只需重新开启“主动消息”和“云闹钟”两个开关即可恢复，无须重新绑定设备。

## 非目标

- 不清除普通聊天回复任务或用户手动发出的消息。
- 不删除角色、聊天记录、朋友圈内容、记忆或 API 配置。
- 不注销 FCM Token，不删除 Cloudflare 的 `sub:<deviceId>` 订阅。
- 不自动重新开启任务；恢复必须由用户主动操作。

## 方案比较

### 方案 A：只清网页字段

仅删除 `pendingProactiveJob` 和 `pendingMomentJob`。实现简单，但 Service Worker 镜像、Android Room 队列和云端旧任务仍会恢复或执行，不能解决当前故障。

### 方案 B：全链路清理并保留绑定（采用）

先冻结本地调度，再清理网页、IndexedDB、Android 原生队列和云端任务；保留设备订阅。它能消除任务源头，也允许用户以后直接重新开启。

### 方案 C：清除应用全部数据

能彻底清理，但会破坏聊天、角色、记忆和配置，不符合保留用户数据的要求。

## 用户界面

在“设置 → 诊断”的操作区新增危险操作按钮：

- 标题：`紧急清空全部自动任务`
- 说明：`保留聊天、角色、配置和云闹钟绑定`
- 点击后弹出确认：`将关闭主动消息和云闹钟，并清空本机与云端的全部主动私聊、朋友圈任务。聊天、角色、记忆、API 配置和设备绑定不会删除。继续？`

执行期间按钮禁用，避免重复提交。完成后显示：

`已清空全部自动任务并暂停调度。云闹钟绑定已保留；重新开启“主动消息”和“云闹钟”即可恢复。`

若只有部分步骤失败，结果必须分别显示“本地网页”“Android 原生”“云端”三部分状态，不能用笼统的成功提示掩盖失败。

## 清理流程

### 1. 立即冻结调度

清理函数首先在内存和持久化设置中强制写入：

- `proactiveEnabled = false`
- `cloudTimerEnabled = false`

同时更新设置页两个选择框。`deviceId`、`pushSubscription`、`nativeFcmToken` 和 `pushTransport` 原样保留。

这一步必须先于任何异步网络请求，以免清理过程中再次补排。

### 2. 清理网页会话任务状态

遍历所有 `allChats`，删除：

- `pendingProactiveJob`
- `pendingMomentJob`
- `cloudScheduleSyncedAt`
- `cloudMomentScheduleSyncedAt`

同时清除主动任务的失败时间、错误文本和调度轨迹，避免状态页继续显示已结束的故障。普通聊天消息、普通回复状态和朋友圈内容不变。

将清理后的设置和聊天写入 localStorage，并把 `rpchat_app_state_updated_at` 更新为当前时间。

### 3. 清理 Service Worker/IndexedDB 镜像

将清理后的完整应用状态写入 `ALMemoryDB` 的 `meta/app_state`，确保 Service Worker 不能从旧镜像恢复已删除任务。

从网页 localStorage 和 `ALMemoryDB` 的 `meta/call_logs` 中删除主动私聊、主动朋友圈及其后台记忆筛选产生的调用日志；保留普通手动聊天和手动连接测试日志。

Service Worker 在处理 `proactive` 推送前必须检查镜像中的 `proactiveEnabled` 和 `cloudTimerEnabled`。任一关闭时直接忽略，不执行模型调用、不安排下一次任务。

### 4. 清理 Android 原生执行层

为 `AlExecution` Capacitor 插件新增批量清理方法，只处理 `PROACTIVE_CHAT` 和 `PROACTIVE_MOMENT`：

- 将未完成的主动任务和活动尝试标记为 `CANCELLED`。
- 将已完成但尚未应用到 UI 的主动任务标记为已处理，防止清理后又写入聊天或朋友圈。
- 删除主动私聊和主动朋友圈快照，使迟到 FCM 的旧 `jobId` 无法通过快照匹配。
- 取消 `AlExecutionWakeWorker` 的唯一工作并停止 `AlExecutionService`，终止当前后台排空循环。

普通 `DIRECT_REPLY` 任务不在批量清理范围内。

Android FCM 收到主动推送时，除校验快照 `jobId` 外，还必须校验快照内的启用状态；清理后的迟到推送直接忽略。

### 5. 清理该设备的 Cloudflare 任务

Cloudflare Worker 新增按设备批量取消端点。请求只携带当前 `deviceId`，服务端执行：

- 删除 `job:mom_<deviceId>_*`。
- 删除 `job:pro_<deviceId>_*`。
- 从所有相关 `due:` 桶移除上述任务 ID；空桶直接删除。
- 保留 `sub:<deviceId>`。
- 不触碰其他设备或测试任务。

响应返回删除的私聊任务数、朋友圈任务数、清理的到期引用数和保留订阅状态。客户端用该响应生成可核验的结果提示。

批量取消必须按 KV 分页读取，不能假设任务少于单页限制。任务归属同时通过键前缀和任务值中的 `deviceId` 校验，避免误删。

## 恢复流程

用户进入设置，将“主动消息”和“云闹钟”重新设为开启并保存：

1. 使用保留的设备 ID 和推送订阅，不重新申请通知权限。
2. 根据当前会话重新创建新任务。
3. 每个会话、每种任务只创建一个新的有效任务。
4. 已清除的旧任务、旧快照和旧错误记录不恢复。

如果保存时发现订阅确实失效，状态页再提示用户重新绑定；正常情况下不出现重新绑定流程。

## 错误处理

- 本地冻结和网页状态清理不得依赖网络，必须优先完成。
- Android 插件不存在时标记“非原生环境”，不视为网页清理失败。
- 云端请求失败时，本地仍保持关闭，按钮提示“本地已停止，云端清理失败，可重试”。
- 重复点击清理是幂等操作；没有任务时返回删除数量 0，仍视为成功。
- 清理过程中禁止调用任何安排下一次任务的函数。

## 测试设计

### 网页与 Service Worker

- 按钮存在，包含明确的保留数据说明和二次确认。
- 清理函数先关闭两个开关，再执行异步步骤。
- 所有会话的两类待执行字段和同步字段被删除。
- 角色、消息、朋友圈、记忆引用、API 配置和订阅字段保持不变。
- 清理后的 `app_state` 覆盖 IndexedDB 旧镜像。
- Service Worker 在开关关闭时忽略主动推送且不补排。
- 调用日志只移除自动任务场景。
- 重复清理得到相同结果。

### Android

- 批量清理只取消 `PROACTIVE_CHAT` 和 `PROACTIVE_MOMENT`。
- `DIRECT_REPLY` 保持不变。
- 活动尝试被取消，未应用的已完成主动任务不会再次写入 UI。
- 主动快照被删除，旧 FCM `jobId` 不再匹配。
- 唤醒工作取消，执行服务停止。

### Cloudflare Worker

- 只删除目标设备的 `mom_` 和 `pro_` 任务。
- 清除对应 `due:` 引用和空桶。
- 保留目标设备订阅、其他设备任务和测试任务。
- 支持分页和重复调用。
- 响应计数准确。

### 回归验证

- 运行现有 Node 基础测试和 Android 单元测试。
- 构建 Android 应用。
- 本地模拟“关闭后存在旧镜像与旧 FCM”的场景，确认不会重新创建任务。
- 部署 Worker 后，用测试设备执行清理，验证云端目标任务为 0、订阅仍存在。
- 重新开启两个开关，验证只生成一组新任务且无需重新绑定。

## 验收标准

- 点击一次后，目标设备的主动私聊和朋友圈任务在网页、IndexedDB、Android Room 和 Cloudflare 中均为 0。
- 清理后等待至少两个 Worker cron 周期，任务数量仍为 0。
- 清理后迟到推送不会触发记忆 AI 或聊天 AI。
- 状态页不再刷新旧的主动任务错误。
- `sub:<deviceId>`、FCM Token 和推送权限保留。
- 重新开启两个开关后功能恢复，并且不会复活旧任务。
- 用户内容和 API 配置无变化。
