# 主动消息 Skip 配额与完整消息上下文设计

## 目标

同时修正两项行为：

1. 用户发言不再重置主动私聊的 skip 配额。任意连续四次已经完成的主动私聊中，最多允许一次 `skip`。
2. 聊天小g和监督小g的近期上下文从“24个原始气泡/消息行”改为“20条完整消息”。一次用户点击“发送完毕”所提交的一组气泡算一条完整消息；虞栖一次生成的一个或多个气泡算另一条完整消息。

记忆小g的证据窗口继续保留最多200条原始消息，不跟随本次20条生成上下文变化。

## 根因

### Skip 配额

当前 `getProactiveChatDeliveryPolicy` 先查询最近一条用户消息，并且只统计这条用户消息之后的主动私聊。结果是用户每次发言都会清空最近主动消息的 skip 历史，使“连续四次最多一次 skip”退化为“每次用户发言后重新获得一次 skip”。

### 生成上下文

当前 `buildGenerationWindow` 按 `messageId` 去重后直接截取末尾24行。这个单位是数据库消息行，不是一次完整表达。历史兼容数据或一次生成拆成多个气泡时，会挤占窗口，使模型看到的实际对话轮次少于设计值。

## 方案比较

### 方案A：只把24改成20

改动最小，但仍以消息行/气泡计数，无法满足用户确认的“完整消息”口径。

### 方案B：在数据库新增永久 `batch_id`

长期结构最明确，但需要数据库迁移、Android协议升级和历史数据回填。本次需求不需要扩大到跨端迁移，风险和工作量偏高。

### 方案C：在生成窗口中按现有权威字段分组（采用）

先按 `messageId` 去重和时间排序，再按“说话方 + turnId”聚合。当前手机端一次“发送完毕”只向桥接提交一个权威 source message，其内容已经合并该批全部用户气泡；虞栖一次生成的多气泡共享同一个 `turnId`，因此可以稳定聚合。没有可靠 `turnId` 的旧数据按单条处理，不猜测历史分组。

此方案不改数据库，不改变手机显示，不影响证据记忆，只改变聊天小g与监督小g所见的近期生成上下文。

## 详细行为

### 主动私聊

- 查询该角色最近四个状态为 `committed`、`delivered` 或 `completed` 的 `PROACTIVE_CHAT`。
- 不再以用户消息时间作为查询下界。
- 四个记录中已有一次 `skip` 时，`skipAllowed=false`。
- 失败任务和其他自动任务类型不占用窗口。
- 返回结构保留 `resetAfterTurnId` 字段以兼容调用方，但固定为 `null`，明确表示不存在用户发言重置点。

### 完整消息窗口

- 输入先按 `messageId` 去重，保留时间较新的同ID记录。
- 排除当前用户消息，避免它同时出现在 `recentMessages` 与 `currentUserMessage`。
- 按发送时间升序排列。
- 分组键优先使用 `speakerType + turnId`。
- 同一 `turnId` 中用户与虞栖分别成组，避免把提问和回复合成一条。
- 缺少 `turnId` 时，每条消息单独成组。
- 截取最近20组，并完整保留组内所有消息，不从中间砍掉气泡。
- 输出仍是扁平消息数组，保持现有 brain/supervisor 请求结构兼容；限制的是组数，不是输出数组长度。

## 验收标准

1. 最近四次主动私聊含一次 skip，之后即使用户发言，下一次仍不允许 skip。
2. 当这次 skip 滑出最近四次主动私聊窗口后，重新允许 skip。
3. 一次用户批次和一次虞栖回复分别占一个完整消息名额。
4. 同一虞栖生成含多个气泡时，20组边界不会切断该生成。
5. 当前用户消息不会重复进入历史。
6. 记忆小g仍收到最多200条原始证据消息。
7. 现有主动消息、路由、监督重写和Android构建测试全部通过。

## 非目标

- 本次不实现私聊图片发送。
- 本次不修改第四轮潜台词人工批注及其预设。
- 本次不迁移旧数据库，也不推测缺少批次信息的历史消息属于同一组。
