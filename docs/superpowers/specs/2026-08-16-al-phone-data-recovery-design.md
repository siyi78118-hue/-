# AL 手机数据只读恢复设计

## 目标

在不清除、不迁移、不覆盖现有手机数据的前提下，处理“Android 原生数据库仍可读，但 Web 角色目录为空”的事故。恢复版必须先保护数据，再盘点来源，最后只在来源明确时恢复；任何歧义都停在只读模式。

本设计不继续普通 1.0.120 发布，不修主动消息或网络桥接，也不把重装、清存储、导入旧备份当作恢复手段。

## 已确认事实

- 手机仍运行 1.0.117，尚未安装本轮准备的 1.0.120。
- Android 系统显示 AL 用户数据仍占 6.17 GB。
- 应用诊断能从原生执行链读取最近完成任务和当前后台扫描记录，说明原生插件及至少一部分 Room 数据仍可读。
- 当前 Web `DB.get()` 会把 JSON 解析失败静默替换成空默认值。
- 当前启动末尾会无条件执行 `mirrorAppStateNow()`，因此空默认值可能被持久化为新的空镜像。
- 当前镜像恢复只比较 `updatedAt`；一个时间较新的空本地状态能够挡住时间较旧但有内容的镜像。

## 安全原则

1. **先冻结，后读取。** 在角色、聊天、朋友圈或设置任一关键槽位解析失败，或 Web 为空但原生仍有角色证据时，禁止所有 Web 状态写入、镜像写入、原生消息落 UI、主动任务和后台恢复。
2. **不以“空”证明删除。** 只有经过验证的 `role_delete_v1` tombstone 才代表角色已删除；角色数组为空、镜像为空或读取异常都不代表删除。
3. **不自动选择有损来源。** 非空有效本地状态优先；其次为非空有效 IndexedDB 镜像；最后才是原生 Room 中可验证的角色快照和消息投影。
4. **只合并，不覆盖。** 恢复只增加缺失角色、聊天和消息，按稳定 ID 去重；不删除任一现有行，不覆盖较完整角色资料。
5. **恢复前后都有证据。** 先保存不含正文的盘点摘要和原始槽位校验值；恢复后记录来源、数量、校验值和时间。正文、API Key、角色提示词不得写入诊断日志。

## 组件

### 1. Web 启动保护器

在 `tavern-app/index.html` 读取全局状态之前建立恢复守卫：

- 分别读取 `rpchat_*` 与旧 `tavern_*` 槽位，记录 absent / valid / invalid，不再把 invalid 静默当成合法空值。
- 对 `settings`、`characters`、`chats`、`moments` 计算仅含类型、数量、字节数和 SHA-256 的摘要。
- 恢复判定结束前，`DB.set()`、`mirrorAppStateNow()`、原生消息 reconcile、主动任务和角色计划同步全部 fail-closed。
- 正常非空数据不改变原有启动路径。

### 2. IndexedDB 镜像读取器

只读检查 `ALMemoryDB/meta/app_state`：

- 不升级、删除或重建 object store。
- 验证镜像结构和角色/聊天引用关系。
- 本地为空而镜像非空时，允许镜像成为候选，不再仅凭时间戳拒绝。
- 本地非空而镜像为空时，禁止空镜像覆盖本地。

### 3. Android Room 只读盘点接口

在 `AlExecutionPlugin` 增加只读接口，由 `RoomExecutionStore` 和 DAO 返回：

- 非 tombstone 角色的稳定 ID；
- 每个角色最新有效 `CharacterSnapshot` 中的名称、玩家名和系统提示词校验信息；
- turn、raw message、reply part、memory、role plan 的数量及时间范围；
- Room 数据库及 WAL/SHM 的文件大小；
- 已验证的角色删除 tombstone 状态。

接口不得写数据库，不返回 API Key，不在诊断日志中写聊天正文。角色提示词仅在用户实际执行恢复时返回，不进入普通盘点结果。

### 4. 恢复判定

按以下顺序选择：

1. 主 localStorage 有效且非空：正常启动，只补充缺失项。
2. 主槽位损坏但旧 `tavern_*` 有效且非空：以旧槽位为候选。
3. Web 为空且 IndexedDB 镜像有效非空：以镜像为候选，即使其时间戳较旧。
4. 两个 Web 来源均无角色，但 Room 有未删除角色：进入恢复界面，显示计数和候选角色，等待用户点击“恢复角色入口”。
5. 来源冲突、多个身份无法对应、存在损坏结构：保持只读冻结，允许导出诊断，不执行猜测性恢复。

### 5. 恢复提交

恢复提交使用两阶段流程：

- 先在 IndexedDB 写入独立 `recovery_candidate_v1`，包含来源摘要、目标摘要和状态 `prepared`，不触碰现有 `app_state`。
- 再写 localStorage 的缺失角色/聊天，重新读取并校验。
- 校验成功后写新的 `app_state`，将 candidate 标为 `committed`，最后解除恢复冻结。
- 任一步失败都恢复提交前快照并继续冻结；不得留下“角色恢复了一半”的状态。

若只能从 Room 恢复，先恢复角色入口和原生可验证消息；头像、仅存在于 Web 的朋友圈展示信息和未进入原生的数据标为“待从旧镜像/备份补齐”，不得伪造。

## 用户界面

异常时覆盖普通首页显示简洁恢复页：

- “检测到手机原生数据仍在，网页角色目录未读取成功；已暂停写入。”
- 展示三个来源的角色数、消息数和状态，不展示正文。
- 提供“恢复角色入口”“复制诊断”两个按钮。
- 隐藏清空、导入、新建角色和普通备份按钮。

正常用户不会看到恢复页。

## 测试与交付门

- 红灯覆盖：损坏 JSON、旧键有效、较新空本地/较旧非空镜像、空镜像不得覆盖、Room 有角色时禁止启动写、tombstone 不得复活、恢复中断回滚、重复恢复幂等。
- Android 真 Room 测试覆盖：只读盘点零写、重启一致、WAL 存在、角色删除过滤、多个角色稳定排序。
- Web 合同覆盖：冻结期间零 `DB.set` / 零 mirror / 零 native apply / 零 proactive；正常非空状态保持原行为。
- 构建门：Web 全门、Android unit、`assembleDebugAndroidTest`、完整 `npm test`。
- 正式 APK 必须同包名、同正式证书、versionCode 递增；安装前核对签名和 SHA-256。无实体设备时不得声称真实手机恢复成功，只能交付“代码与构建门通过、待手机覆盖安装验证”。
