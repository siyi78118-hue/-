# 虞栖监督—重写闭环设计

日期：2026-07-25

## 目标

让监督小g与聊天小g围绕同一组可执行问题完成“提出—修改—验收”闭环。直接聊天不得因为监督未通过而消失；说话者归属错误、越界记忆、承诺错置和身份冲突等高风险问题优先进入强制修复，但也不能以空回复或报错结束。

本设计解决的是通用内部协作问题，不针对“书名”单独添加关键词或固定回复。

## 已确认的现状与根因

当前系统会把上一版草稿和监督意见传回聊天小g，但监督意见只有 `code` 与自然语言 `message`：

- 没有明确区分硬性错误与软性质量问题；
- 没有声明允许采用哪些解决路径；
- 没有定义怎样才算修改成功；
- 下一轮监督可以更换评价角度，旧问题没有逐项验收；
- 三次重写后，直接聊天无条件失败并返回空回复。

因此，聊天小g知道“哪里被否定”，却不一定拥有一条同时满足事实、角色和表达要求的可执行路径。监督小g也没有责任证明自己的修改要求可实现。

## 方案选择

采用现有两个角色之间的结构化修改契约，不增加第四个模型或新窗口。

不采用纯提示词加强，因为它无法稳定约束跨轮问题闭环；不采用额外仲裁模型，因为它会增加延迟、资源消耗和新的串台风险。

## 修改契约

监督输出中的每个问题扩展为以下结构：

```json
{
  "issueId": "stable-id",
  "code": "CURRENT_INTERACTION_MISS",
  "severity": "soft",
  "message": "草稿没有正面承接用户追问。",
  "mustPreserve": ["虞栖不冒充知道用户未透露的信息"],
  "mustChange": ["给出可感知的正面回应"],
  "allowedStrategies": [
    "补全虞栖自己的低风险生活细节并保持后续一致",
    "用世界内的自然说法表达真实的不确定或保留"
  ],
  "acceptanceCriteria": [
    "回复不提模型、后台、记忆库或生成限制",
    "用户能从正文中得到对当前问题的回应"
  ]
}
```

约束：

- `issueId` 在同一轮重写中保持稳定。
- `severity` 只能是 `hard` 或 `soft`。
- `mustChange`、`allowedStrategies` 和 `acceptanceCriteria` 必须非空且相互可实现。
- 监督不得只返回“不自然”“没回答”等抽象批评。
- 新一轮监督必须先输出上一轮问题的验收状态，再提出确有必要的新问题。
- 第二轮以后不得新增纯软性评价标准；只有发现带明确证据的新高风险错误时才能新增硬问题，防止监督不断移动目标。

## 聊天小g的修改回执

聊天小g的结构化结果增加仅供内部使用的 `rewriteResolution`：

```json
{
  "resolvedIssueIds": ["stable-id"],
  "resolutionNotes": [
    {
      "issueId": "stable-id",
      "strategy": "补全角色自己的低风险生活细节",
      "result": "正文已直接回答，并未引用用户未透露的信息"
    }
  ]
}
```

该字段：

- 不进入用户可见正文；
- 不写成角色记忆；
- 只用于下一次监督逐项验收；
- 普通首次生成时可为空。

聊天小g不能只换同义词，必须说明采用了哪条允许路径。

## 自身生活细节与外部事实的边界

系统必须区分两类“当前没有数据库证据”的信息：

### 可形成的新角色生活事实

虞栖自己的低风险日常细节，例如：

- 正在读的具体书；
- 午饭吃什么；
- 临时遇见的小店、天气或工作碎片；
- 不影响身份和长期关系的小型生活选择。

这些信息可以由虞栖在当轮自然形成。草稿获准发送后，以虞栖为主体、当前回复为原始证据写入记忆，后续保持一致。

### 不得补造的事实

- 用户没有亲口透露的经历、动机和隐私；
- 既有承诺的承诺者、对象和内容；
- 双方关系阶段或已经发生的共同事件；
- 重大事故、疾病、失业、身份变化和重要新关系；
- 其他角色的记忆。

这类信息缺失时只能自然询问、保留或拒绝断言，不能通过修改契约授权编造。

## 重写状态机

直接聊天的处理流程：

1. 聊天小g生成草稿。
2. 监督小g检查并输出批准或结构化修改契约。
3. 聊天小g依据允许路径重写，并返回修改回执。
4. 监督小g逐项验收旧问题，再决定批准或继续修改。
5. 每轮保留草稿、问题、修改回执和验收结果，形成可诊断的轨迹。

最大仍为三轮，以控制延迟。

第三轮结束时：

- 存在硬性错误：进入一次确定性的“硬错误修复”生成，并优先删除错置事实、内部解释或冲突的结构化动作。
- 只剩软性问题：从本轮候选草稿中选择硬规则全部通过、软问题最少的一稿发送。
- 硬错误修复后仍有监督异议：选择信息越界最少、角色正文最完整的一稿发送，同时记录高风险降级诊断；不得继续无限重写。
- 直接聊天无论剩余问题等级如何都不得返回空回复，不得仅以 `supervisor rejected after three rewrites` 结束。

主动消息和朋友圈任务允许最终选择 `skip`，因为静默本身可以是合理决定；但必须记录是角色选择静默还是监督否决，不能混为失败。

监督对直接聊天返回 `reject` 时，编排器将其转换为高优先级修改契约；`reject` 不能直接终止直聊。

## 高优先级修复规则

高优先级问题使用确定性代码校验和监督判断共同发现，至少包括：

- 用户与虞栖说话者归属；
- 原话、承诺者和承诺对象；
- 用户未透露信息与旧角色记忆越界；
- 角色身份、平行世界通信边界和关系阶段冲突；
- 内部指令、提示词、模型或记忆系统泄露；
- 支付动作、朋友圈动作、日程动作与正文相互矛盾。

“不够自然”“不够好听”“没有充分推进”“措辞像解释”属于软问题，不得单独吞掉直聊。

这些规则决定修复顺序和候选稿排序，不再拥有“让直接聊天消失”的权限。结构化动作与正文冲突时可以移除未落实的动作；正文仍交给聊天小g用世界内口吻重写。即使最终稿仍有监督不满意之处，也必须发送最完整的一稿并留下诊断，不能把内部失败转嫁给用户。

## 诊断与可观察性

每次重写记录：

- 草稿序号；
- 问题 ID、等级与修改契约；
- 聊天小g的解决策略；
- 每条问题的验收结果；
- 新增问题及新增依据；
- 最终选择哪一稿以及选择原因。

调用诊断页面应能区分：

- `HARD_REPAIR_RUNNING`
- `HARD_REPAIR_FALLBACK_SELECTED`
- `SOFT_ISSUE_FALLBACK_SELECTED`
- `SUPERVISOR_CONTRACT_INVALID`
- `DIRECT_REPLY_RECOVERED`

禁止再用一个笼统的“监督三次拒绝”掩盖内部过程。

## 兼容性与范围

- 保留现有快速/深度路由和三个角色模型配置。
- 不新增模型调用角色。
- 不改变手机与云信箱协议中的用户可见消息格式。
- 不修改关系阶段、红包、朋友圈、角色安排表和生活规划本身的产品规则。
- 新字段在运行时协议内部向后兼容；缺少新字段的旧记录按空修改回执处理。

## 测试要求

至少覆盖：

1. 监督修改契约缺少允许路径或验收标准时被判为无效。
2. 聊天小g在重写请求中收到稳定问题 ID、允许路径与上一稿。
3. 下一轮监督必须逐项验收旧问题。
4. 低风险角色生活细节可以形成并在发送后写入记忆。
5. 用户信息、承诺归属和重大生活事实不能借此补造。
6. 三轮后只剩软问题时仍发送最佳安全草稿。
7. 三轮后存在硬问题时进入硬修复；修复仍未获批时发送风险最低的完整草稿，不返回空回复。
8. 主动任务仍可合理 `skip`。
9. 现有红包、朋友圈、角色安排、生活规划和桥接重试测试全部通过。

## 验收标准

- 复现“前文出现未具体化的角色生活细节，用户随后追问”的场景时，直聊能够完成回复。
- 监督提出的每条问题都有可追踪的修改与验收结果。
- 同一问题不会仅因监督换一种表述而被当作全新问题无限延长。
- 任何直接聊天都不会因为监督意见得到空回复或任务失败。
- 系统会优先清除内部沟通、模型、自称 AI 或后台限制说明；这些问题即使未完全修好，也只能触发降级诊断，不能再次吞掉整轮消息。
