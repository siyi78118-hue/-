# 虞栖云信箱 VPN 代理与积压恢复设计

日期：2026-07-20  
状态：已选定方案，待用户审阅后实施

## 1. 背景与已确认事实

手机通过云信箱发送消息成功，Cloudflare 中目前保留两封尚未被电脑领取的加密信件：

- 07:06 的 `PROACTIVE_CHAT` 主动任务；
- 09:45 的 `DIRECT_REPLY` 普通聊天请求。

09:45 信件中携带 16 条恢复记录，其中 02:41 的两条旧主动消息已经具备正确的证据字段：发送者为 `yuqi`、类型为 `character`、来源为 `legacy_fallback`，原始时间与原文均保留。

电脑端记忆库尚未消费这两封信，当前同步游标与云投递记录仍为空。直接网络测试表明：

- Node 直接访问 Cloudflare 超时；
- 当前由 Node 隐藏启动的 PowerShell 系统网络适配器同样超时；
- Node 24 使用 `--use-env-proxy`，并令 HTTP/HTTPS 走 `http://127.0.0.1:10809` 后，访问云信箱健康接口成功返回 HTTP 200；
- 本机 VPN 代理正在监听 `127.0.0.1:10809`，SOCKS 代理监听 `127.0.0.1:10808`。

根因是电脑桥接没有显式使用 VPN 本地代理，同时轮询异常在后台被静默吞掉，导致服务健康页显示正常，但云信箱始终无人领取。

## 2. 目标

1. 仅让虞栖电脑桥接的云端 HTTP/HTTPS 请求经过本机 VPN，不改变 Windows 全局代理。
2. 本机和局域网连接继续直连，保留 AUTO（局域网优先）体验。
3. VPN 暂时关闭时不丢失、不确认删除云端信件；VPN 恢复后自动重试。
4. 云信箱连接失败必须在日志、诊断与健康状态中可见。
5. 恢复当前积压：07:06 的过时主动任务不迟到发送，09:45 的普通消息正常进入记忆与聊天链路。
6. 02:41 的旧主动消息以正确发送者、来源、时间写入电脑原始消息账本，并由记忆小g执行只记忆、不回复的补记。

## 3. 不在本次范围内

- 不修改手机与 Cloudflare 的配对密钥、设备编号或加密密钥。
- 不修改 Windows 全局代理、WinHTTP 代理或 VPN 客户端配置。
- 不改变局域网地址、端口、防火墙规则或手机 AUTO 连接策略。
- 不借本次修复调整虞栖人物设定、提示词或模型路由。
- 不上传 GitHub；本次仅在本地项目中实施与验证。

## 4. 选定方案

### 4.1 配置

在 `yuqi-runtime/config.json` 的 `cloudRelay` 下加入非敏感代理设置：

```json
{
  "proxy": {
    "enabled": true,
    "url": "http://127.0.0.1:10809",
    "noProxy": "127.0.0.1,localhost,::1"
  }
}
```

示例配置同步增加同样结构，但不写入任何真实设备密钥。

### 4.2 启动方式

`scripts/start-yuqi-background.ps1` 在创建 Node 进程前：

1. 读取并校验代理 URL，只接受本机 HTTP/HTTPS 代理地址；
2. 设置子进程继承的 `HTTP_PROXY`、`HTTPS_PROXY` 与 `NO_PROXY`；
3. 使用 Node 24 的 `--use-env-proxy` 参数启动运行时；
4. 保留原有隐藏窗口、日志重定向、PID 文件与启动健康检查。

代理设置只存在于虞栖桥接子进程环境中，不写入 Windows 全局环境变量。

### 4.3 云端请求实现

显式代理开启时，`yuqi-runtime/src/main.mjs` 使用已受 `--use-env-proxy` 控制的原生 `fetch`。未开启代理时保留现有系统网络适配器作为兼容路径。

手机到电脑轮询、电脑到手机回复投递以及云信箱 ACK 必须共用同一个代理感知的 `fetch`，避免只修复收信而无法回信。

## 5. 数据流

### 5.1 正常收信

1. 手机把加密信件写入 Cloudflare。
2. 电脑桥接通过 `127.0.0.1:10809` 轮询 `phone_to_pc`。
3. 电脑在本机解密信封。
4. 如信封带有恢复记录，先执行幂等补录并调用记忆小g；补录过程不生成聊天回复。
5. 普通消息在电脑数据库中持久化为待处理 turn；只有持久化成功后才 ACK 对应的 `phone_to_pc` 信件。
6. turn 进入既有快速/深度路由，生成虞栖回复；待发送回复由本机 outbox 持久化管理。
7. 回复通过相同代理写入 `pc_to_phone`，投递失败时留在 outbox 重试。
8. 手机收到回复与 `recoveryAckSeq`，不再重复上传已经确认的历史记录。

### 5.2 VPN 不可用

1. 轮询失败时不 ACK 云端信件。
2. 后台按既有轮询周期继续重试，不创建兜底回复、不改变同步游标。
3. 诊断状态记录最近失败时间、阶段和简短错误；相同错误限频写入，避免日志爆量。
4. VPN 恢复后自动继续领取，无须用户重新发送。

### 5.3 过时主动任务

云端主动任务在领取时若已经超过 30 分钟：

1. 先幂等处理信封内的恢复记录；
2. 标记为 `stale_proactive_suppressed`；
3. 不启动聊天小g、不向手机补发迟到的主动消息；
4. 确认删除该云端任务，随后继续处理更新的普通消息。

本次 07:06 主动任务符合该规则；09:45 普通消息不受此规则影响。

## 6. 可观察性与错误处理

云轮询组件维护以下非敏感运行状态：

- `enabled`：云信箱是否启用；
- `proxyEnabled`：是否启用专用代理；
- `connected`：最近一次云请求是否成功；
- `lastSuccessAt`：最近成功时间；
- `lastErrorAt`：最近失败时间；
- `lastError`：不含令牌、密钥和正文的短错误；
- `pendingProcessed`：最近一次轮询成功处理数量。

`/v1/health` 返回上述摘要，手机诊断页可据此显示“云信箱正常”或“VPN代理不可用”。任何日志和健康接口均不得输出设备令牌、加密密钥、配对密钥或聊天正文。

## 7. 测试设计

实施必须遵循测试驱动流程，先写失败测试再写实现。

### 7.1 启动脚本契约

- 代理开启时包含 `--use-env-proxy`；
- 子进程继承正确的 HTTP/HTTPS 代理；
- `NO_PROXY` 至少覆盖本机地址；
- 代理关闭时保持旧启动路径。

### 7.2 云轮询单元测试

- 代理 fetch 同时用于 poll、enqueue 与 ACK；
- poll 失败时信件不 ACK、同步游标不前进；
- 错误进入限频诊断；下一次成功会清除连接错误状态；
- 30 分钟以上的主动任务只补记并抑制发送；
- 普通消息不因等待时间而被抑制。

### 7.3 回归测试

- 局域网 `/v1/health` 与手机本地桥接不经过代理；
- 快速/深度模型路由不变；
- 恢复包中的发送者与来源不被改写；
- 同一恢复包重复出现时不会重复写入或重复调用记忆小g；
- 云回复仍为端到端加密，Worker 只保存密文。

## 8. 本次积压验收

修复并重启后必须同时满足：

1. 云信箱 `phone_to_pc` 积压从 2 降为 0；
2. 07:06 主动任务产生抑制诊断，不产生可见虞栖消息；
3. 09:45 用户消息成为已提交 turn，并产生专属小g回复；
4. 同步游标前进到至少 16；
5. 02:41 两条消息进入电脑原始账本，发送者为 `yuqi`，来源为 `legacy_fallback`；
6. 记忆补录只调用 memory 角色，不产生第二条回复；
7. 电脑将回复成功写回云信箱，手机能够收到；
8. 生成新的本机记忆快照，快照包含补录后的消息账本。

## 9. 回滚

如代理路径异常：

1. 停止虞栖后台服务；
2. 将 `cloudRelay.proxy.enabled` 设为 `false`；
3. 恢复未带 `--use-env-proxy` 的启动路径；
4. 重新启动服务。

云端未 ACK 的信件仍然保留，回滚不会丢失聊天记录。任何回滚不得删除手机聊天、本机数据库或记忆快照。
